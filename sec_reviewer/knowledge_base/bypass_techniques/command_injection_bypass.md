#### 1. 弱黑名单清洗（字符替换/阻断）
当专家追踪数据流，发现开发者试图通过限制或替换特定字符（如使用 `replace()`、`in` 关键字、或简单字符列表）来进行防御时，此类清洗极易被以下手法绕过：

* **空格被过滤/清洗**: 
  * **Code特征**: 代码试图剔除或拦截空格 ` `。
  * **绕过Payload**: 
    * Linux: 使用内部字段分隔符 `${IFS}`（如 `cat${IFS}/etc/passwd`）；使用输入重定向符 `<`（如 `cat</etc/passwd`）；在 Bash 中使用花括号扩展 `{cat,/etc/passwd}`。
    * Windows: 使用 `%ProgramFiles:~10,1%` 等环境变量切片，或在 PowerShell 中使用 `,` 分隔参数。
* **命令分隔符被过滤/清洗**: 
  * **Code特征**: 代码替换或拦截了分号 `;` 或常规管道符 `|`。
  * **绕过Payload**: 
    * 逻辑控制符: 使用 `&&`（前必真）或 `||`（前必假）来串联命令。
    * 内联执行: 使用 `$()` 或反引号 `` `whoami` ``，系统会优先执行内联命令并将结果喂给外层命令。
    * 换行符注入: 注入 `\n` (`%0a`) 或 `\r` (`%0d`)。在很多解析器或 Shell 环境中，换行符会直接开启一个完全独立的命令上下文。
* **敏感关键字被过滤/清洗**: 
  * **Code特征**: 代码禁止出现 `cat`、`sh`、`etc`、`passwd` 等敏感词。
  * **绕过Payload**: 
    * 引号打断: `c'a't /e"t"c/pas\swd`（单双引号闭合不影响 Linux 路径解析）。
    * 反斜杠转义: `c\at /e\tc/p\asswd`。
    * 变量拼接: `a=c; b=at; $a$b /etc/passwd` 或利用空变量 `cat$u /etc$u/passwd`（`$u` 未定义为空字符串）。
    * 通配符模糊匹配: `/bi?/c*t /e?c/pa*wd`（直接触发 glob 机制执行 `cat /etc/passwd`）。
    * Windows 特性: Windows 下可使用 `c^a^t c:\w^i^n^d^o^w^s\w^i^n.ini`（`^` 为 cmd 转义符，执行时会被剥离）。

#### 2. 缺陷正则表达式（边界校验不严）
当专家发现开发者使用正则表达式（如 `re.match`、`preg_match`）来校验输入（例如限定只能输入 IP 或域名）时，必须严格审视正则的边界符号：

* **缺乏首尾限定符 (如仅使用 re.match)**: 
  * **漏洞机制**: Python 的 `re.match` 仅从字符串**开头**开始匹配。若正则为 `r"\d+\.\d+\.\d+\.\d+"`，输入 `1.1.1.1; id` 时，开头部分完全合法，正则校验通过。若后续代码将整个原始输入传给了命令执行函数，则导致注入。
  * **研判标准**: 必须检查正则是否在末尾显式使用了 `$` 或 `\Z` 锚定结束边界。
* **多行模式漏洞 (Multiline 逃逸)**: 
  * **漏洞机制**: 即使正则使用了 `$` 结尾，如果开启了多行匹配模式（如 Python 的 `re.M` 或 PHP 的 `/m` 修饰符），`$` 将匹配“每行的末尾”而非“整个字符串的末尾”。
  * **绕过Payload**: 攻击者可以通过传入包含换行符的数据（如 `127.0.0.1\nid`）绕过前缀校验，在第二行注入恶意命令（正则在匹配到第一行后就已经成功）。

#### 3. 误区防御（不安全的包裹与类型转换）
当专家发现开发者试图用特定语法“包裹”用户输入，认为包裹后就安全时，需高度警惕以下逻辑逃逸：

* **单/双引号包裹防御**: 
  * **典型错误**: `f"ping '{user_input}'"` 或 `f'echo "{user_input}"'`。
  * **绕过Payload**: 攻击者输入 `127.0.0.1'; id; '` 即可轻松闭合引号并逃逸（最终命令：`ping '127.0.0.1'; id; ''`）。
  * **专家提示**: 拼接字符串是防御引号逃逸的重灾区。在 Python 中，只有使用 `shlex.quote()` 进行转义才是唯一标准；若直接拼接，则存在高危风险。
* **容器类型转换（如 str(list) / str(dict)）**: 
  * **典型错误**: 开发者认为将输入放入列表，再用 `str([user_input])` 转成字符串会自带单引号保护，例如正常输入 `test` 变成 `['test']`。
  * **绕过Payload**: 如果攻击者故意传入包含单引号和命令替换的数据（如 `$(id)'`），Python 在序列化列表时，**为了保护内部的单引号，会自动将外层包裹切换为双引号**！最终输出变为 `["$(id)'"]`。当此字符串被带入 Shell 时，双引号无法阻止 `$()` 的执行，从而引发命令注入。

#### 4. 参数注入（Arguments Injection）
当专家发现代码中显式设置了 `shell=False`（或使用了安全的进程派生 API，如 `subprocess.Popen(array)`），看似无法通过原生管道符注入命令时，必须检查**被调用的二进制文件本身**：

* **漏洞机制**: `shell=False` 只能阻止 Shell 解析器（如 bash/cmd）对关键字（`;`、`|`）的解析，但外部输入仍然作为独立的参数传递给目标程序。如果被调用的二进制程序支持敏感的、具备执行代码能力的命令行标志（Flags），攻击者通过注入以 `-` 或 `--` 开头的参数，依然能实现 RCE。
* **典型高危命令清单及绕过参数**: 
  * `find` ➡️ 利用 `-exec` 参数 (如 `find . -name *.txt -exec sh -c "id" \;`)
  * `tar` ➡️ 利用 `--checkpoint-action` 参数 (如 `tar -cf /dev/null a --checkpoint=1 --checkpoint-action=exec=sh`)
  * `wget` / `curl` ➡️ 利用 `-O` 或 `-o` 参数覆盖系统关键文件（如 `.bashrc`、计划任务），或下载后门。
  * `git` ➡️ 利用 `--ext-cmd` 或通过特定的配置参数注入。
  * `ln` / `mv` / `cp` ➡️ 劫持符号链接或覆盖合法文件。
* **专家研判标准**: 
  当追踪到外部输入作为参数直接传递给上述高危二进制文件时（即使 `shell=False`），检查开发者是否在外部输入参数前强制使用了 `--`（参数终止解析符）。例如：`["tar", "cf", "archive.tar", "--", user_input]` 是安全的。如果缺乏 `--`，且输入可控，则存在**高危参数注入风险**。
